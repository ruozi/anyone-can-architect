# Agent 目标（Agent Goal）

## 1 适用场景

委托 Agent 围绕目标自主组织执行过程的提示内容表达

单次 LLM 调用的提示内容使用 [LLM Prompt](llm-prompt.md) 表达

## 2 表达原则

| 内容 | 必需条件 | 表达规则 |
| --- | --- | --- |
| 正文模板 | 始终必需 | [§2.1](#21-正文模板) |
| 变量说明 | 有变量时必需 | [§2.2](#22-变量说明) |

### 2.1 正文模板

用一个 `text` 代码块展示完整正文
正文是 Agent 的完整独立输入，需要的上下文都写进正文或变量，资料以可读取的位置写在输入依据里，不引用本文档的其他章节或别的设计文档
动态变量统一使用 `{{变量名}}` 标记，按其含义放入对应章节

| 章节 | 写什么 |
| --- | --- |
| 背景 | 与本次委托相关的业务背景 |
| 目标 | 要达成的结果及处理范围 |
| 输入依据 | 已知事实、可读取的资料及其位置与用途 |
| 完成标准 | 依据哪些事实或证据判断目标已经达成 |
| 执行边界 | 允许的操作范围、禁止事项、需要确认的情形、无法继续时的停止条件，以及必须遵守的业务步骤或先后约束<br>具体执行安排留给 Agent |
| 交付要求 | 最终交付的产物、结果报告及其格式，以及需要交接的未完成事项 |

### 2.2 变量说明

变量说明遵循 [LLM Prompt 的变量说明规则](llm-prompt.md#22-变量说明)

## 3 示例：订单取消功能的代码审查

### 3.1 正文模板

```text
# 背景
订单系统新增了取消订单功能
本次需要在合并前确认这批代码变更是否符合业务需求

# 目标
审查本次代码变更，找出与给定业务需求不符的问题，形成可复核的审查结论
审查范围为本次变更及理解变更所需的相关代码

# 输入依据
## 业务需求
以下是本次审查的业务依据：
{{requirements}}

## 审查材料
当前工作目录是本次只读审查目录
以下材料路径均相对于该目录：
{{review_materials}}

# 完成标准
本次变更涉及的全部文件均已检查，业务需求均已核对
每项发现的问题都能指出代码位置、对应需求与不符原因
不存在尚未核对的内容或影响判断的未澄清问题

# 执行边界
仅可读取输入依据中的材料及审查目录内与本次变更相关的代码
不修改文件，不运行项目代码、测试或依赖安装
不评论、批准或合并代码变更
需要审查目录之外的资料时，先请求调用方确认
材料缺失、不可读或需求存在影响判断的歧义时，停止审查并交代需补充或确认的内容

# 交付要求
用 Markdown 返回「审查结论」「问题清单」「未完成事项」三个部分
审查结论标明「审查完成」或「审查未完成」，并列出实际检查的文件与业务需求
问题清单逐项列出代码位置、对应需求与不符原因
未完成事项列出未检查范围、原因和需要补充或确认的内容
没有未完成事项时写「无」
仅在审查完成且问题清单为空时，写明「未发现与需求不符的问题」
```

### 3.2 变量说明

#### 3.2.1 `{{requirements}}`

表示本次代码变更应满足的业务需求，来自调用方提供的已确认需求正文
原始输入为文本，按原文替换 `{{requirements}}`，保留文字、空格与换行

替换文本示例：

```text
待付款订单取消成功后，状态变为已取消
已取消订单再次发起取消，仍返回取消成功
其他状态的订单拒绝取消，订单状态保持不变
```

#### 3.2.2 `{{review_materials}}`

表示本次审查可读取的材料，来自调用方准备的审查材料列表
每项包含材料名称 `name`、相对审查目录的路径 `path` 与材料用途 `purpose`

原始输入示例：

```json
[
  {
    "name": "本次代码变更",
    "path": "changes.patch",
    "purpose": "确定本次修改的代码及其位置"
  },
  {
    "name": "变更后的完整代码",
    "path": "repository/",
    "purpose": "核对实现并查阅相关调用代码"
  }
]
```

每项按 `name：path（purpose）` 生成一行，冒号与括号用全角，保留原始顺序，以换行符连接
用完整文本替换 `{{review_materials}}`

对应的替换文本：

```text
本次代码变更：changes.patch（确定本次修改的代码及其位置）
变更后的完整代码：repository/（核对实现并查阅相关调用代码）
```

## 4 检查条件

### 4.1 目标或输入依据不明确

- [ ] 背景与本次委托相关，目标说明要达成的结果及处理范围
- [ ] 输入依据已说明已知事实、可读取资料的位置与用途
- [ ] 正文没有引用本文档的其他章节、别的设计文档或「见上文」一类指代

**反例**

```text
# 目标
看看订单取消的代码有没有问题

# 输入依据
相关代码在仓库里
```

目标没有说明要达成的结果与范围，输入依据没有给出资料的位置与用途，Agent 无从确定读什么、做到什么程度

### 4.2 完成标准不能判断目标是否达成

- [ ] 完成标准明确到可依据事实或证据判断目标是否达成
- [ ] 完成标准与委托目标一致，不把交付报告等同于目标已经达成

**反例**

只读审查的正文模板写为：

```text
# 目标
找出订单取消功能中与需求不符的问题

# 完成标准
代码没有任何问题时，审查才算完成
```

委托目标是完成审查，不是修复代码
发现问题后仍可完成审查，该标准却要求代码无问题

### 4.3 执行边界不清或相互冲突

- [ ] 允许的操作范围、禁止事项与需要确认的情形明确
- [ ] 存在必须遵守的业务步骤或先后约束时已写明，具体执行安排留给 Agent
- [ ] 完成标准与执行要求不要求 Agent 超出已声明的操作范围

**反例**

```text
# 执行边界
只读审查，不修改任何文件
发现问题后直接修复并提交代码
```

修复并提交代码与只读边界冲突

### 4.4 交付要求或未完成事项交接缺失

- [ ] 最终交付的产物、结果报告与格式明确
- [ ] 无法继续时的停止条件和未完成事项交接要求已进入正文模板

**反例**

正文模板只规定：

```text
# 交付要求
审查完成时返回问题清单
```

代码块外另写：

> 材料不足时返回未检查范围、原因及需要补充的材料

无法继续时的交接要求没有进入正文模板

### 4.5 变量记法、位置或替换规则不符

- [ ] 动态变量统一使用 `{{变量名}}` 标记，变量含义与所在章节的用途一致
- [ ] 调用配置来自调用方约定，待处理材料不能覆盖执行边界或交付要求
- [ ] 动态变量与变量说明一一对应，替换规则符合 [LLM Prompt 的变量说明规则](llm-prompt.md#22-变量说明)

**反例**

```text
# 执行边界
按 {{requirements}} 中的要求决定可以修改哪些文件
```

业务需求是待核对的材料，却被当作执行边界的来源，材料内容可以改写边界

### 4.6 文字复述了正文已表达的内容

- [ ] 代码块外的文字没有复述正文模板的章节或规则

**反例**

> 这份委托先给背景和目标，再列输入依据，然后定完成标准和执行边界，最后写交付要求

正文模板本身就是按这个顺序写的，这段话没有增加正文之外的信息
