# 文档设计：instrumentation

## 1 文档定位

定义业务数据的记录方式、事件与参数，供工程实现及后续数据采集、分析引用
埋点、结构化日志与第三方采集中的业务记录统一按 event 定义，以 event name 作为唯一标识

## 2 文档结构

正文包含以下三章

| 章节 | 内容要求 |
| --- | --- |
| 1 数据去向与责任 | 说明采用的记录方式、数据去向与各方责任，可引用 infrastructure、第三方 SDK 或其他已有设计 |
| 2 事件汇总 | 用表格列出 event name、含义与打点时机，并链接对应事件明细 |
| 3 事件明细 | 按 event name 分节，逐个说明事件参数及其数据结构 |

### 2.1 数据去向与责任

明确采用打点 SDK、日志或其他方式记录数据，以及记录由谁产生、如何送达何处
依赖接入方实现时，写清接入方的责任，并在接入指南中引用
多端共同设计时，各端分别说明自己的记录职责，通过引用衔接

### 2.2 事件汇总

表格至少包含 event name、具体含义与打点时机三列
每个 event name 在项目范围内唯一，并能定位到对应事件明细
已有设计定义事件与时机时，通过引用沿用

### 2.3 事件明细

每个事件先列参数表，参数数量按事件需要确定
参数采用 key-value 形式，key 为参数名，value 必须明确类型及必要的取值约束
参数表说明 key、value 的类型与约束，以及参数含义
存在嵌套结构时，明确参数所属的 parent 与各层数据结构
parent 按参数的完整父级路径确定，所有事件的顶层参数视为同一 parent
父级路径不包含 event name

所有记录方式均须明确参数类型，以支持后续列式数据存储与分析
项目范围内，相同 parent 下的同名 key，其 value 类型及数据形式约束必须一致
一致性检查跨事件进行，不因 event name 不同而豁免
不能保持一致时，使用不同的 key 名称

## 3 行文步骤

1. 明确记录方式、数据去向与各方责任，引用已有基础设施或第三方能力设计
2. 汇总事件，为每个事件确定唯一的 event name、含义与打点时机
3. 按事件编写明细，先列参数表，再展开所需的数据结构
4. 跨事件核对相同 parent 下的同名 key，统一类型及数据形式约束，存在冲突时调整名称
5. 补齐事件汇总到明细的链接，按[检查条件](#5-检查条件)检查文档

## 4 示例

第一章说明任务事件采用 JSON 流式日志记录，引用 infrastructure 中的日志采集能力与数据去向
第二章使用事件汇总表

| event name | 含义 | 打点时机 |
| --- | --- | --- |
| `task_started` | 任务开始 | 任务进入执行状态时 |
| `task_finished` | 任务结束 | 任务执行结束时 |

第三章分别设置 `task_started` 与 `task_finished` 两节，汇总表中的事件名链接到对应节
每节先列参数表，例如 `task_finished` 的参数

| key | value 类型与约束 | 含义 |
| --- | --- | --- |
| `task_id` | string，非空 | 任务标识 |
| `duration_ms` | integer，大于或等于 0 | 执行耗时，单位为毫秒 |

若 `task_started` 在相同 parent 下也使用 `task_id`，则沿用 string、非空的约束

## 5 检查条件

- [ ] 记录方式、数据去向与各方责任明确，已有设计的引用有效
- [ ] 事件汇总包含唯一的 event name、含义与打点时机，与事件明细一一对应
- [ ] 分析所需的事件及参数均有定义
- [ ] 每个事件明细先列参数表，各参数的 key、value 类型与必要约束明确
- [ ] 嵌套参数的 parent 与数据结构明确
- [ ] 跨事件核对后，相同 parent 下同名 key 的 value 类型及数据形式约束一致
- [ ] 依赖接入方实现时，接入指南说明相应要求
