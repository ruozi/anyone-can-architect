# 文档设计：distribution

## 1 文档定位

定义已固化版本面向接入方或用户的制品构建、交付、验证与故障处置流程，包括更新、撤回与版本退回方式

## 2 文档结构

第一章定义分发前提，包括版本与制品、接收对象、目标平台、渠道与签名条件

第二章按本项目的实际顺序展开分发流程
每步定义执行方式、通过条件、失败处理与恢复位置
构建、签名、上传、审核与交付等阶段按实际需要组织

第三章定义交付验证与故障处置，包括制品取得、安装或接入验证、撤回、更新与已交付版本的处理
定义整体验证标准，由相关分发与处置步骤引用
定义渠道与已安装、已接入版本的退回边界，不能退回时定义替代处置方式

各章按实际内容[层层深入](../../skills/references/drill-down.md)，不固定平台、渠道或小节模板

结构示意：

```text
## 1 分发前提
## 2 分发流程
### 2.1 <执行阶段>
### 2.2 <执行阶段>
…
## 3 交付验证与故障处置
### 3.1 <验证或处置内容>
### 3.2 <验证或处置内容>
…
```

## 3 行文步骤

1. 确定分发前提
   - 定义 release 锁定的版本来源、接收对象、目标平台、渠道与所需权限
   - 定义制品名称、版本、源码提交与摘要的对应关系，以及构建和签名所需条件
   - 定义交付范围，包括安装包、SDK、接入文档或用户手册
2. 设计分发流程
   - 按依赖关系安排构建、签名、上传、审核、交付与生效等操作
   - 为每一步定义执行方式、通过条件、失败处理与恢复位置
   - 定义凭据来源与使用方式，以及缺失或失效后的处理
   - 涉及渠道审核、缓存或分批交付时，定义等待、状态查询与生效条件
3. 定义交付验证
   - 定义制品身份、渠道可见性、取得、安装与接入的检查动作和通过条件
   - 核对随包文档与实际制品一致，示例能够用于目标平台
   - 定义首次交付与更新后的整体验证标准
4. 定义故障处置与后续维护
   - 区分尚未交付、渠道已生效与用户已安装或接入的状态，分别定义处置流程
   - 定义撤回、停止更新、恢复旧制品或交付修正版的条件、操作与结果验证
   - 定义版本兼容与更新路径，不能退回时定义替代处置方式
   - 定义旧制品与验证记录的保留和清理范围
5. 按 [§2](#2-文档结构)组织各章，核对完整流程
   - 各平台与渠道的制品身份已登记，能够追溯到对应的固化版本
   - 各步骤的结果满足后续前提，恢复执行不会重复发布或覆盖错误制品
   - 服务端运行与故障处置引用 [deployment](deployment.md)，合入与版本固化引用 [release](release.md)

## 4 示例

````markdown
# 报告 SDK 分发

## 1 分发前提

| 内容 | 定义 |
| --- | --- |
| 版本来源 | release 锁定的 v2.0.0 |
| 接收对象 | 使用 Python 的业务工程 |
| 制品 | aca_report_sdk-2.0.0-py3-none-any.whl |
| 目标环境 | Python 3.11 与 3.12 |
| 渠道 | 公司私有 Python 包索引 |
| 源码与制品身份 | release-manifest.json 记录 Tag、源码提交、文件名与 SHA-256 |
| 发布权限 | 专用账号仅能上传 aca-report-sdk 包，凭据由流水线密钥存储提供 |
| 随包文档 | 接入指南与版本变化说明 |
| 兼容条件 | v2.0.0 与 v1.9.0 使用相同的报告服务 API |

本 SDK 没有独立本地数据库，退回版本不涉及持久数据迁移
业务工程通过依赖锁文件选定版本，渠道上传不会自动更新已接入工程
构建结果、清单与验证记录保存在发布流水线的制品存储中

## 2 分发流程

### 2.1 构建并登记制品

**执行**：检出 v2.0.0，运行 `bash scripts/build-sdk.sh v2.0.0`
脚本构建 wheel，将制品版本、源码提交与摘要写入发布清单

**通过**：源码提交等于 Tag 指向，包版本为 2.0.0，制品摘要与清单一致

**失败与恢复**：不上传，修正构建环境后重试
源码需要修复时回到版本固化流程，使用新版本，不修改 v2.0.0

### 2.2 验证制品与文档

**执行**：运行 `bash scripts/verify-sdk.sh --local v2.0.0`，在两个目标 Python 版本的独立环境中安装本次 wheel，按 §3.1 验证

**通过**：两个环境均通过验证，随包指南对应 2.0.0，示例只使用公开接口

**失败与恢复**：不上传，保留失败记录
涉及制品或随包文档修正时使用新固化版本，从 §2.1 重新执行

### 2.3 上传并验证渠道

**执行**：运行 `bash scripts/publish-sdk.sh v2.0.0`，上传制品与发布清单，查询渠道状态

**通过**：接收方身份能够取得制品，下载摘要与发布清单一致，再按 §3.1 验证通过

**失败与恢复**：上传结果未知时先查询渠道
同名同版本文件存在且摘要一致时，不重复上传，继续验证
同名同版本文件摘要不一致时停止并报告，不覆盖渠道制品
渠道已可取得但验证失败时执行 §3.2

## 3 交付验证与故障处置

### 3.1 交付验证

验证任务使用专用测试账号与测试报告服务，不操作正式业务数据

| 检查 | 通过条件 |
| --- | --- |
| 制品身份 | 下载文件名、包版本与 SHA-256 等于发布清单 |
| 安装 | 两个目标 Python 版本均能在独立环境中安装并导入 SDK |
| 接入 | 按随包指南初始化，通过公开接口生成并下载测试报告 |
| 更新 | 从 v1.9.0 更新到 v2.0.0 后，已有调用方式仍可完成同一业务 |
| 验证清理 | 本次测试报告与对象均已删除 |

### 3.2 分发故障

- 尚未上传：停止交付，保留验证记录，使用修正版重新固化并分发
- 渠道已生效：标记 2.0.0 为撤回版本，停止推荐安装，保留原文件与发布清单
- 已安装或接入：通知接入方停止更新，并将依赖锁文件恢复为 1.9.0，在独立环境重装后验证业务
- 无法退回：使用新的修复版本，按本流程完成交付，由接入方更新并验证

撤回渠道版本不会删除接入方已经安装的代码
每个接入方确认实际版本与验证结果后，才记录该工程完成恢复

### 3.3 后续更新与保留

更新使用新的固化版本，重复 §2 的构建、验证与上传流程
接入方先验证兼容性，再修改依赖锁文件，升级方式见[接入指南](../user-guide/integration-guide.md)

已交付制品、清单与验证记录持续保留，不覆盖已发布的同版本文件
未上传的失败构建保留 30 天后清理
报告服务的部署与故障处置见[deployment](deployment.md)
````

## 5 检查条件

- [ ] 版本来自 release 固化的 Tag，制品名称、版本、摘要与源码提交可追溯
- [ ] 接收对象、目标平台、渠道、构建与签名条件及所需权限已定义
- [ ] 分发流程覆盖全部必要操作，每步有执行方式、通过条件、失败处理与恢复位置
- [ ] 凭据来源、使用方式及缺失或失效行为已定义，没有实际凭据值
- [ ] 涉及审核、缓存或分批交付时，等待、查询与生效条件已定义
- [ ] 整体验证覆盖制品身份、渠道取得、安装或接入，以及版本更新
- [ ] 随包文档与实际制品一致，示例适用于目标平台
- [ ] 尚未交付、渠道已生效与用户已安装或接入的状态分别有故障处置
- [ ] 撤回、退回与更新的适用边界已定义，无法退回时有替代处置与结果验证
- [ ] 恢复执行不会重复发布或覆盖错误制品，旧制品与验证记录的保留和清理范围已定义
