# Doc Design: infrastructure

## 1 Purpose

Design of the infrastructure that this project needs to build or depend on, defining dependency scope, usage, and resource structure

Business processing belongs in the corresponding business design doc
Deployment operations and environment configuration delivery belong in [deployment](deployment.md), and security reasoning belongs in [security](security.md)

## 2 Structure

Use an overview table in the first chapter to list the infrastructure, its purposes, and links to detailed designs
Each overview row corresponds to a subsequent chapter, with a separate chapter for each infrastructure item

Apply [drill-down](../../skills/references/drill-down.md) in each chapter based on its actual content, without predefined resource categories or subsection templates

- Define resource locations, capabilities used, consumers, and access methods
- Define the required resource configuration, data structures, and storage organization by resource type
- Define permissions, lifecycle, migration, and consistency requirements as needed

Structure outline:

```text
## 1 Infrastructure Overview
## 2 <infrastructure>
### 2.1 <specific content>
#### 2.1.1 <specific content>
## 3 <infrastructure>
…
```

## 3 Writing Steps

1. Inventory the infrastructure that this project needs to build or depend on, and list its purposes and consumers
2. Define the dependency scope and usage of each infrastructure item
   - Distinguish resources to build from existing resources
   - Identify the instances, databases, buckets, directories, or service endpoints used
   - Define the capabilities used, access methods, configuration items, and identity permissions
   - Reference existing access contracts and delivery locations for configuration and credentials
   - Record only credential sources, never actual values
3. Detail the resource configuration for each infrastructure item, and the structures, identifiers, and maintenance ownership of related data or objects
4. Add the required constraints
   - For persistent data, define retention, update, deletion, and necessary recovery requirements
   - For migrations, define execution order, records, transaction boundaries, compatibility, and failure handling
   - For data stored in multiple locations or derived data, define sources, updates, and consistency requirements
   - Reference the corresponding business design docs for business read/write, retry, and compensation flows
5. Organize chapters according to [§2](#2-structure), and add links to detailed designs in the overview table
   - Verify consistency among the resource overview, detailed designs, and consumer references

## 4 Example

```markdown
# Infrastructure

## 1 Infrastructure Overview

| Infrastructure | Purpose | Detailed design |
| --- | --- | --- |
| PostgreSQL | Store report records and object references | [§2](#2-postgresql) |
| S3 | Store generated report files | [§3](#3-s3) |
| File gateway | Provide temporary access links for report files | [§4](#4-file-gateway) |

## 2 PostgreSQL

### 2.1 Access

The report module uses the `public` schema in the `reporting` database
The application identity can read and write report records, and the migration identity performs structural changes

| Configuration item | Purpose | Source |
| --- | --- | --- |
| `REPORT_DB_HOST` | Database endpoint | [Database configuration](deployment.md#21-postgresql) |
| `REPORT_DB_PORT` | Database port | [Database configuration](deployment.md#21-postgresql) |
| `REPORT_DB_USER` | Application identity | [Database identity](deployment.md#21-postgresql) |
| `REPORT_DB_PASSWORD` | Application identity credentials | [Database credential delivery](deployment.md#21-postgresql) |

### 2.2 Report Data

#### 2.2.1 Report Records

Each row in `reports` stores the identity and file reference of a generated report
The [report module](module-report/README.md) owns maintenance

| Field | Type | Nullable | Default value | Meaning |
| --- | --- | --- | --- | --- |
| `report_id` | `UUID` | No | None | Report identifier generated by the report module |
| `object_key` | `TEXT` | No | None | Full object key of the S3 report file |
| `content_sha256` | `TEXT` | No | None | SHA-256 digest of the report file |
| `created_at` | `TIMESTAMPTZ` | No | `CURRENT_TIMESTAMP` | Record creation time |

| Name | Type | Definition |
| --- | --- | --- |
| `pk_reports` | PRIMARY KEY | `(report_id)` |
| `uq_reports_object` | UNIQUE | `(object_key)` |
| `ix_reports_created` | INDEX | `(created_at)` |

See the [report module design](module-report/README.md) for coordination between file writes and record commits

## 3 S3

### 3.1 Usage Scope and Access

The report module uses a dedicated bucket, whose name is injected through `REPORT_BUCKET` in the [S3 configuration](deployment.md#22-s3)
The application identity can only read and write the bucket's `reports/` prefix, and the file gateway can only read that prefix
The bucket does not allow anonymous access, and identity delivery is described in the [S3 deployment configuration](deployment.md#22-s3)

### 3.2 Report Files

| Item | Definition |
| --- | --- |
| Object key | `reports/{report_id}/report.csv` |
| File format | UTF-8 CSV with the header `date,completed_count,overdue_count` |
| Data types | date is an ISO date, and both counts are non-negative integers |
| Report ownership | The PostgreSQL reports record references the file through object_key |
| Content validation | The file digest matches reports.content_sha256 |
| Update rules | Report files cannot be overwritten, and new reports use new report_id values |
| Retention rules | Registered report files are retained indefinitely, with no automatic cleanup in this version |

## 4 File Gateway

### 4.1 Integration

Use the existing file gateway's link issuance capability, with the interface contract defined in the [gateway integration doc](../reference/file-gateway.md)
The report module passes only object keys of registered reports, and the gateway accesses S3 with a read-only identity

| Configuration item | Purpose | Source |
| --- | --- | --- |
| `FILE_GATEWAY_URL` | Gateway endpoint | [Gateway configuration](deployment.md#23-file-gateway) |
| `FILE_GATEWAY_TOKEN` | Caller identity credentials | [Gateway credential delivery](deployment.md#23-file-gateway) |

### 4.2 Usage Constraints

Issued links are valid for 15 minutes and allow only reading the specified object
See the [report module design](module-report/README.md) for business authorization of access links and handling of issuance failures
```

## 5 Checklist

- [ ] The overview covers the infrastructure to build or depend on, with one detailed design chapter for each resource
- [ ] The dependency location, capabilities used, consumers, and access methods are defined for each resource
- [ ] Detailed designs apply drill-down based on actual content
- [ ] Required resource configuration, data structures, and storage organization are defined, along with related identifiers and maintenance ownership
- [ ] Where lifecycle, migration, or storage in multiple locations is involved, the corresponding rules and consistency requirements are defined
- [ ] Configuration and credential sources are recorded, with no actual credential values
- [ ] Business processing, deployment operations, and security reasoning reference the corresponding docs without repeating their details
